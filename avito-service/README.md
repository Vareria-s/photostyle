# ФотоСтайл → Avito

Сервис односторонне готовит каталог Tilda для Avito. Python 3.12 и стандартная библиотека выполняют расчёт в GitHub Actions; отдельный Cloudflare Pages relay выдаёт готовый snapshot. PDF-сервис и его workflows работают отдельно.

Для подключения один раз добавьте **AVITO_CLIENT_ID** и **AVITO_CLIENT_SECRET** через [GitHub → Settings → Secrets and variables → Actions](https://github.com/Vareria-s/photostyle/settings/secrets/actions), кнопка **New repository secret** для каждого значения. Это персональные ключи владельца нужного аккаунта Avito. Не отправляйте их в чат и не записывайте в файлы проекта. Других полей, JSON, CSV или ручного разрешения активации не требуется. [Короткая инструкция](docs/подключение.txt).

Следующий часовой запуск автоматически проверит доступ, действующий профиль и успешную загрузку, полную копию прежнего feed, идентичности объявлений и схемы категорий. Если проверки достаточны, подготовит snapshot, опубликует его, сверит публичный файл и только затем заменит адрес управляемого feed с сохранением прочих feeds и расписания. Проверка текущего результата Avito идёт отдельно. Токен получается заново по той же паре; вручную обновлять access token не нужно.

**Подключённый профиль, доступный feed и принятые Avito объявления — разные этапы.** Пока провайдер обрабатывает файл по своему расписанию, run показывает незавершённую проверку и завершается ошибкой, а не объявляет интеграцию успешной. Принудительный `POST /autoload/v1/upload` не используется: он игнорирует ограничения расписания. `success_warning` также не считается полным успехом.

Автоматизация не может достоверно восстановить исходную карточку по одному списку API: там нет полного текста, фото и SKU. Нет полного прежнего feed, однозначной связи, поддерживаемой схемы или прав — видимый blocker в Actions, исходный профиль остаётся прежним. Новые товары добавляются только при доказанном отсутствии дубля, уникальном SKU и достаточных фактах по схеме; неоднозначные или неполные исключаются. Это не обещание полного переноса всего каталога Tilda. Старые объявления сохраняются, включая отсутствующие в Tilda. Причины и счётчики доступны в `/report.json` и `/status.json`. [Доказанные ограничения API](docs/account-contract.md), [эксплуатация](docs/runbook.md).

Защита от неполной выгрузки сравнивает число исходных offers и число проверенных товарных групп с прошлым расчётом: по умолчанию падение ниже 70% блокирует публикацию. `candidate_count` считает прошедшие проверку группы после allowlist; `feed_ad_count` отдельно считает объявления файла, включая сохранённые старые. Идентичность UID, варианта и SKU/Id сохраняется при временном отсутствии или ошибке товара. Длинные Title/Description сокращаются по целым словам до активного ограничения схемы; исходный и конечный текст фиксируются в отчёте и CSV. Пустое описание Tilda для существующей карточки использует проверенное историческое описание, чтобы обновление цены не терялось только из-за пустого текста.

Пользователь подтвердил: все товары в продаже новые. Это подтверждённый факт для состояния продаваемых товаров; дополнительный ввод Condition не требуется. Прокат исключён из этого правила. Допустимое значение поля и прочие обязательные свойства всё равно проверяются по схеме конкретной категории Avito.

Публичный сервис: [photostyle-avito.pages.dev](https://photostyle-avito.pages.dev). `/health` и `/status.json` показывают время snapshot, blockers и stale; `/preview.xml`, `/report.json`, `/reasons.csv`, `/text-changes.csv` — диагностику. `/feed.xml` закрыт до разрешённой подготовки и при snapshot старше 4 часов; `/state.json` закрыт. `production_enabled=true` означает готовность локального snapshot к выдаче, а не доказательство принятия Avito. Не считайте статический текст стартовой страницы текущим статусом: проверяйте Actions и JSON.

Workflow `PhotoStyle Avito hourly snapshot` работает каждый час на 17-й минуте (`17 * * * *` UTC; в Екатеринбурге также 17-я минута), при изменениях своего кода в main и через Actions → Run workflow. Это расписание подготовки Tilda, а не расписание загрузки Avito. GitHub может задержать cron; настройки Avito сохраняются. Отсутствуют оба секрета — продолжает работать прежний preview. Введён только один — запуск останавливается. Ошибка account prepare не заменяет последний корректный snapshot и не переключает профиль.

Ветка `avito-feed` публикуется одним fast-forward push: полный snapshot, затем `current.json` со SHA. HTTP читает status/feed по одному immutable SHA; указатель может кэшироваться до 60 секунд. Account commit ожидает ограниченное время появления точного нового digest, проверяет свежесть и профиль повторно. При отказе после публикации новый snapshot остаётся опубликованным, но workflow не откатывает его к старому hash и не меняет профиль вслепую. Публикации сериализованы; force/rebase не используются.

Между запусками `state.provider_outbox` сохраняет до 256 версий: digest, имя feed, ожидаемые идентификаторы, резервирование SKU/Id новых объявлений и отпечатки профиля. `provider_receipts` хранит проверенные квитанции Avito. Почасовой запуск продолжает пересчитывать текущий Tilda, пока Avito работает по своему расписанию: ожидание старой версии не замораживает цены и остатки. Запоздалая квитанция связывается с конкретным digest из очереди; принятие старого файла не означает принятие последнего. Неразрешённое ожидание более 7 суток или переполнение очереди даёт явный blocker вместо потери контекста.

Если после публикации профиль остался исходным и приватный plan потерян, следующий запуск сверяет отпечатки/идентификаторы и пересчитывает данные из текущего Tilda. Для уже свежего неизменившегося файла время `data_generated_at` сохраняется; устаревшие цены не получают новую дату без пересчёта. Полные профили и credentials остаются только во временном защищённом plan и не включаются в очередь.

`source_sync_complete` и `source_sync_coverage=complete|partial` показывают охват Tilda. Готовность безопасно переключить профиль (`ready_for_profile_switch`) учитывается отдельно: частичный охват не выдаётся за полный перенос каталога. Принятие конкретного файла Avito также проверяется отдельно. Создание новых объявлений проката сейчас не поддерживается этим сервисом (`rental_CREATE_not_supported_in_service`); это ограничение реализации, а не доказанный запрет Avito.

Приватный план с исходным профилем хранится с закрытыми правами только в `RUNNER_TEMP/avito-account` на время запуска и удаляется на завершающем шаге. Он не попадает в Git, staging, Actions artifacts или ZIP. Это временная резервная копия для переключения и компенсации ошибки, не долговременное хранилище профиля. В summary нет email, телефона, исходных profile URLs или credentials. Публичные диагностические файлы могут содержать опубликованные товарные идентификаторы и тексты; секретных ответов API в них нет.

Проверки из корня проекта:

```powershell
python -m unittest discover -s avito-service/tests -v
node --test avito-service/tests/worker.test.mjs
python avito-service/tools/check_publication.py
python avito-service/tools/package.py --out work/packages
```

ZIP собираются детерминированно по явному списку публичных исходников. Pages ZIP содержит только `_worker.js`, `_routes.json`, `index.html` в корне; source ZIP — исходники, тесты, инструкции и один Avito workflow. Произвольные отчёты, локальные планы, профили и credentials не включаются. Большие расчёты и state не размещают в main. При изменении состава исходников агент обновляет список упаковки.

Пример автономного preview для разработчика (путь вывода должен отсутствовать):

```powershell
$outPath = Join-Path $env:TEMP ('photostyle-avito-' + [guid]::NewGuid().ToString('N'))
python avito-service/converter.py --config avito-service/config.json --source-file avito-service/fixtures/catalog.yml --state work/previous/state.json --out $outPath
```

Это команда диагностики, не дополнительный этап подключения аккаунта пользователем.
