Прямое чтение портала и JSON в этой сессии закончилось HTTP 429; свежая схема не получена. Ограничение не обходилось.

Для проектирования разобрана **копия документации самого провайдера**, а не описание стороннего интегратора: [OpenAPI по закреплённой ревизии](https://github.com/MissiaL/avito-api/blob/9dac805f6887c2a21fba7a7c71e4ca6ece8d0bbc/references/avito-api-openapi.json), [руководство auth той же ревизии](https://github.com/MissiaL/avito-api/blob/9dac805f6887c2a21fba7a7c71e4ca6ece8d0bbc/references/sections/auth.md). [Происхождение копии](https://github.com/MissiaL/avito-api/blob/9dac805f6887c2a21fba7a7c71e4ca6ece8d0bbc/references/sources.md): исходная выгрузка 03.10.2026, попытка повторной проверки 18.10.2026 также 429. Содержимое соответствует сохранённой схеме; соответствие действующему API 27.11.2026 и доступам клиента **не доказано**. Отказ или неизвестная структура ответа должны закрывать активацию, а не включать guessed fallback.

Практическая первичная проверка 27.11: `GET https://api.avito.ru/autoload/v1/user-docs/tree` без токена возвращает **401**. Категории/поля нельзя считать загруженными до подключения аккаунта. Внешние каталоги/шаблоны через запрещённые браузером адреса не открывались.

## Авторизация

Базовый адрес Business API — `https://api.avito.ru`. Персональный режим предназначен для своего аккаунта. `POST /token`, `Content-Type: application/x-www-form-urlencoded`, поля:

```text
grant_type=client_credentials
client_id=<AVITO_CLIENT_ID>
client_secret=<AVITO_CLIENT_SECRET>
```

Успешный JSON содержит `access_token`, `token_type`, `expires_in`. Руководство описывает 24 часа, но программа должна брать срок из ответа. Последующие запросы: `Authorization: Bearer <access_token>`. При персональной авторизации новый токен получают той же парой; refresh token для этого режима не нужен. Ввод в GitHub Actions Secrets, значения не включать в URL, stdout, ошибки, артефакты, состояние или public Git.

Авторизация пользователя кнопкой OAuth является другим режимом: предварительная регистрация приложения, его `client_id/client_secret`, HTTPS Redirect URI и обработчик callback. Consent URL использует `https://avito.ru/oauth`, `response_type=code`, `pro_users_flow=true`, `client_id`, `scope` (перечисление через запятую). После callback `code` обменивается на access/refresh tokens; затем обновляются оба токена. Руководство указывает год для refresh token. Это **не** готовая кнопка входа без зарегистрированного приложения. Scope `autoload:reports` называется доступом к отчётам; нельзя из названия делать вывод, что он разрешает изменение профиля. У операций автозагрузки в сохранённой объединённой схеме отсутствует OAuth security declaration, у ряда операций явно задан только bearer header; это не доказательство анонимного или OAuth-write доступа.

Для этого магазина предусмотрен персональный режим. Само наличие пары не доказывает доступ к автозагрузке/нужному тарифу или что ключи принадлежат главному владельцу магазина.

## Пользователь и имеющиеся объявления

`GET /core/v1/accounts/self` → объект с `id` (integer), `email`, `name`, `phone` (первый подтверждённый телефон), `phones` (массив), `profile_url`. Схема не объявляет обязательность этих полей: проверять нужные значения при получении. Адреса магазина этот метод не возвращает.

`GET /core/v1/items?per_page=99&page=1&status=active,old,removed,blocked,rejected` → `{resources:[...],meta:{page,per_page}}`. Каждая запись: `id`, `title`, `price`, `status`, `url`, `address`, `category:{id,name}`. Нет описания, фотографий, SKU, полного набора XML-характеристик. Нет `total/pages`: завершать после пустой/короткой страницы, с общим пределом страниц и обнаружением повторов. Метод ограничен 25 запросами/минуту. В документации отдельно отмечено, что для сотрудника компании список может быть пустым: требуются ключи владельца объявлений. Пустой ответ не даёт права считать миграцию ненужной.

`GET /autoload/v2/items/ad_ids?query=<avito_id,...>` → `{items:[{avito_id:integer,ad_id:string|null}]}`; `avito_id` обязателен, отсутствие `ad_id` не означает свободный новый товар.

`GET /autoload/v2/items/avito_ids?query=<ad_id,...>` → `{items:[{ad_id:string,avito_id:integer|null}]}`. Это связь старого идентификатора файла и номера Avito, **не** связь SKU магазина и карточки. Лимит размера batch в сохранённой схеме не указан: ограничивать локально и обрабатывать отказ, не выдумывать provider limit.

В Tilda данного магазина SKU находится в `param name="Артикул система"`; `vendorCode` отсутствует. SKU полезен лишь если такой же идентификатор присутствует в исходном полном feed Avito. Уникальность надо проверять с обеих сторон; совпадение названия или цены не является доказательством идентичности. Устойчивый ключ Tilda — `group_id`, вариант — `offer@id`.

## Профиль автозагрузки

`GET /autoload/v2/profile` → обязательные ключи:

```json
{
  "autoload_enabled": true,
  "feeds_data": [{"feed_name": "существующее имя", "feed_url": "https://example.com/feed.xml"}],
  "report_email": "existing@example.com",
  "schedule": [{"rate": 1, "weekdays": [0], "time_slots": [0]}]
}
```

Значения выше показывают форму, **не** рекомендуемые настройки. `feeds_data` может быть `null`; `report_email` в ответе nullable. `schedule` — массив: `rate` integer, `weekdays` — 0…6 (понедельник…воскресенье), `time_slots` — 0…23, часовые интервалы **по Москве**. `rate` — количество объявлений в период; произвольно ставить большое число нельзя. `GET` может вернуть 404 (профиля нет), 403, 400, 500. Не приравнивать 403/429/ошибку сети к отсутствию профиля.

`POST /autoload/v2/profile`, JSON, обязательны `feeds_data`, `schedule`, `autoload_enabled`, `report_email` (строка, уже не nullable). `agreement:boolean|null` дополнительно **обязателен, если профиль создаётся впервые** — это согласие с правилами Автозагрузки. Пустой email не подставлять. Перед изменением сохранить исходный профиль в защищённом хранилище и сверить актуальную версию. Обновление передаёт весь массив feeds: нельзя потерять посторонние фиды/расписание или оставить старый и новый фид с одинаковыми Id одновременно. Новое расписание должно учитывать тариф/лимиты аккаунта, которых одна эта схема не объясняет. Успех POST — HTTP 200 без обещанного JSON тела. После POST обязательно GET для проверки сохранения.

Старые `upload_url`/`feed_url` в корне профиля устарели; использовать `feeds_data`. В схеме нет отдельного endpoint для частичной замены одного feed.

## Последняя выгрузка и копия старого файла

`GET /autoload/v4/uploads/last_successful` → `upload_id`, `stats`, `events`, `feed_urls:[{name,url}]`; опциональные/nullable `status`, `source`, `started_at`.

**`feed_urls[].url` — ссылка на копию файла на момент начала этой загрузки.** Это предпочтительный источник полной исходной XML-карточки для миграции. В `feeds_data[].feed_url` находится живой источник, который мог уже измениться. Сверить имена и IDs с отчётом, не считать произвольный сегодняшний feed полным историческим состоянием. Если полного файла нет/он неизвестного формата, перечисление API не восстановит descriptions/SKU/характеристики автоматически.

Статусы: `processing`, `success`, `success_warning`, `error`. `success_warning` означает завершённую обработку с проблемами части объявлений. Даже last_successful не равен «все объявления опубликованы». 404 означает, что подходящей загрузки нет; это не подтверждает отсутствие старых объявлений. `feed_urls` могут содержать чувствительную ссылку; не публиковать URL с query/credentials в public отчётах. Скачать только разрешённый HTTPS источник, с защитой SSRF/редиректов и bounded response.

`GET /autoload/v4/uploads/last_successful/items?perPage=100&page=1` → `{items:[...],meta:{page,pages,perPage,total}}`. `perPage` 1…100, `page` от1. Опциональные `query` (Id из файла через запятую или `|`) и `sections` (slug через запятую). Элемент:

```text
ad_id:string [required]
section:{slug,title} [required]
messages:[{code,description,title,type,updated_at}] [required]
avito_id:integer|null
avito_status:active|old|blocked|rejected|archived|removed|null
avito_date_end:date-time|null
feed_name:string|null
url:string|null
```

`GET /autoload/v4/uploads/current` и `/current/items` имеют такую же концепцию текущей загрузки. История: `GET /autoload/v4/uploads` (`perPage`, `page`, `dateFrom`, `dateTo`). Обход страниц должен проверять consistency upload_id: последняя загрузка может смениться между запросами; перечитать ID до/после, при изменении повторить подготовку. Дубли/расхождения/неполные страницы не допускают смену источника.

Старые отчёты v2/v3 помечены deprecated; сохранённое руководство указывает отключение 08.03.2027. Новую реализацию строить на v4.

## Дерево категорий и правила полей

`GET /autoload/v1/user-docs/tree` → `{categories:[node...]}`. Узел: `name` обязателен, `slug` опционален, `nested` — массив дочерних узлов. Схема `nested` в сохранённом OpenAPI описана неоднозначно (дополнительные свойства с массивами узлов), поэтому надо поддержать проверенные реальные формы, неизвестную форму блокировать. Только узел со `slug` пригоден для запроса полей; slug нельзя конструировать транслитерацией.

`GET /autoload/v1/user-docs/node/{node_slug}/fields` → `{node:{name,slug},fields:[...],alert?}`. Есть `If-Modified-Since`, ответ `Last-Modified`; 304 имеет пустое тело и требует прежний кэш. Для первого запроса conditional header не посылать. Возможны 400/403/404.

Поле: `tag`, `label`, `descriptions`, `feed_format` (`xml`,`excel`), `content` (массив альтернативных правил), опциональные `children` (вложенные поля с собственными content). Правило:

```text
field_type: input|select|checkbox
data_type: string|integer|float
required:boolean
required_by_dependency:boolean
values:[{value:string,description?:string}]?
default:{value:string,description?:string}|null
values_range:{min:integer|null,max:integer|null}|null
dependencies:[{action:visible|required|hidden,clause:or|and,
                pairs:[{clause:value|filled|empty,source_field_tag:string,values:[string]}]}]?
values_link_json:string|null
values_link_xml:string|null
is_catalog:boolean?
name_in_catalog:string|null
warnings:[{title,content}]|null
```

`values_range` для string ограничивает длину, для integer/float — числовой диапазон. `select` — одно из разрешённых значений, `checkbox` — одно или несколько. Каталожные значения могут отсутствовать в `values` и быть доступны по ссылке. Для `values_link_json` схема обещает определённую структуру, но отдельной response schema этого URL в сохранённом OpenAPI нет. Не угадывать её; при неизвестной форме блокировать соответствующий новый товар, а не объявлять его валидным. `values_link_xml` не имеет гарантированного единого формата.

Контент без dependencies доступен. В массиве альтернатив должен остаться один применимый набор правил; отсутствие применимого набора может означать недоступность поля до заполнения управляющего. `visible` делает поле доступным, `required` меняет обязательность, `hidden` запрещает заполнение. Неизвестное/неразрешённое условие не равно false. Несколько одновременно применимых несовместимых правил — ошибка схемы, не выбор первого. Состояние вещи/состояние комплекта/тип продавца и другие факты нельзя выводить из одного schema default: нужен подтверждённый Tilda param или прежняя карточка. Текущая категория сайта может не совпадать один-к-одному с Avito; неоднозначность не устраняется токеном.

## Запуск и приёмка

`POST /autoload/v1/upload` запускает обработку ссылок из профиля, не принимает XML в body. Успех — HTTP 200, ответ с JSON не обещан. Не чаще одного раза в час. **Метод игнорирует лимиты количества публикаций из настроек автозагрузки и публикует/активирует всё, что возможно.** Поэтому автоматическая миграция не должна бездумно вызывать upload после каждого изменения или считать его безопасной «проверкой». Предпочтительно сохранить согласованное расписание/лимиты и наблюдать его результат; если вызывается upload, предусмотреть полный контроль состава и тарифа до вызова.

В исследованной схеме **нет endpoint сухой проверки полного XML** без публикации. Проверка структуры/обязательных полей локально возможна по полученным правилам; приёмка модерацией, условиями тарифа и текущими ограничениями выполняется только площадкой после загрузки. Локальная успешная проверка не даёт права ставить `avito_validator_passed=true`, будто провайдер уже принял файл.

## Что реально автоматизировать после подключения

Можно автоматически авторизоваться, получить owner ID и контакты, существующий профиль, снимок старого feed, связь старых Id/AvitoId, актуальные правила категорий, построить миграцию при однозначных идентичностях, сформировать и опубликовать собственный feed, затем переключить только управляемый источник и проверить результаты расписания. Это не требует ручного редактирования пользователем CSV/JSON.

Нельзя заранее гарантировать, что любой аккаунт и любой каталог заработают только от наличия двух Secrets: права/тариф, первый agreement, недостающий подтверждённый seller email/phone, недоступный старый файл, неоднозначные SKU, неизвестные товарные факты и отказ модерации не создаются из API. Нельзя гарантировать сохранение всей старой карточки по одному `/core/v1/items`. При такой ситуации сервис должен сохранять старую работающую автозагрузку и показывать конкретное препятствие; не публиковать дубли и не выдавать часть товаров за полный перенос. Это граница внешнего провайдера и исходных данных, а не повод добавлять ручные activation flags.
