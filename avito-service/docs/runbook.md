## Тестовый аккаунт

После доступа агент получает доступность и расписание автозагрузки, актуальный официальный XML шаблон/справочник обязательных свойств категорий, реквизиты продавца и официальный валидатор/отчёт. Для каждой используемой категории заполнить `categories[UID].fields`, `required`, `param_fields` по реальному шаблону и поставить validated=true только после проверки. Нельзя считать товар готовым из-за совпадения названия категории. Проверить исходные/преобразованные title/description в text-changes.csv и подтвердить text_transform_confirmed только после содержательной проверки; длинные тексты уже отмечены в отчёте.

Использовать отдельный test account_scope, account_kind=test и `test_allowlist` из 1–3 реальных product UID (group_id, не случайный вариант). Реквизиты — тестового аккаунта. State и migration отдельные; клиентский state не переносить в тест и наоборот. По умолчанию production закрыт, поэтому агент сначала готовит preview, передаёт XML официальному валидатору и сверяет каждое обязательное поле. Если валидатор требует URL, агент организует отдельное согласованное тестовое размещение/загрузку файла; нельзя преждевременно ставить avito_validator_passed=true для обхода проверки. После реального успешного валидатора, проверки автозагрузки, категории, продавца, тестовой миграции и текста выставить соответствующие activation flags и mode=production для тестового scope. Не расширять allowlist. Запустить, подключить URL тестовому аккаунту, получить реальный отчёт Avito и проверить Id/AvitoId, цену, фото, отсутствие дублей, обновление цены. Снятие товара проверить через подтверждённый площадкой DateEnd; только затем retirement.confirmed=true. Удаление строки из файла само по себе снятием не считать.

## Миграция клиента — обязательный барьер до production

Одной config.migration недостаточно: она связывает ID текущих Tilda товаров, но не сохраняет старые объявления, отсутствующие в первом YML. Агент обязан импортировать начальный опубликованный state из прежнего источника и кабинета. Автоматического импортёра здесь нет: до построения, сверки и рецензии этого state `migration_verified` остаётся false и клиентская production запрещена.

Получить резервную копию полного старого фида, последнего успешного отчёта и списка реально активных объявлений клиента с Id/AvitoId. Сопоставить каждый старый Id с Tilda product UID по надёжным SKU/ссылке/ручной проверке; неоднозначности не угадывать. Создать таблицу сверки: UID, вариант, прежний Id, AvitoId, активность и решение сохранить/снять/разобрать. Проверить уникальность обоих ID и охват ВСЕХ старых активных объявлений, включая отсутствующие в YML. Не создавать новые ID для уже опубликованных товаров.

Агент строит reviewed state version=1, account_scope клиентского аккаунта, generated_at UTC, source_count/candidate_count/eligible_uids из проверенного текущего preview (для корректного drop guard). В items включить ВСЕ прежние активные объявления: ключ — сопоставленный product UID; поля `id`=старый Id, `avito_id`=реальный AvitoId, `variant_id`=UID выбранного варианта, `published`=true, `ad_xml`=полный валидный старый элемент Ad с неизменёнными идентификаторами и обязательными полями. Для отсутствующего в Tilda старого объявления сохранить отдельный согласованный уникальный legacy UID (например legacy:<старый Id>) и полный ad_xml; оно должно попасть в reviewed план снятия, а не потеряться. Не включать в imported state тестовые идентификаторы. `config.migration[UID]` содержит `Id` и `AvitoId`; migration_account_scope должен совпадать с клиентским scope. Все ранее активные записи должны сохраняться в items даже при отсутствии в новом источнике.

Сохранить копию reviewed imported state и запустить конвертер с `--state imported-state.json` в отдельный ещё не существующий staging: `--out` отвергает даже существующую пустую папку. Не выполнять mkdir для целевого пути; конвертер сам публикует полный каталог snapshot одним переименованием. Для каждого повтора использовать новый путь, отличный от пути предыдущего state. До отключения старого фида проверить diff: неизменность Id/AvitoId, отсутствие новых дублей, все старые активные объявления распределены на продолжение/подтверждённое снятие, корректные DateEnd для отсутствующих/Под заказ/недоступных. Для preview снятий retirement.confirmed включать лишь после проверки правил аккаунта; production пока закрыт. Этот новый staging вместе с импортированными published записями агент публикует в avito-feed через snapshot.py, сохраняя резервную копию доимпортного snapshot. Остановить расписание Avito workflow на время импорта, чтобы hourly run не перезаписал импорт; включить после сверки. Не отключать PDF workflows.

Только после сверки полного state, официальной схемы/валидации, контактов клиента, доступности автозагрузки и пользовательского разрешения на переключение выставить клиентские activation flags, mode=production; получить feed и проверить его официальным валидатором перед заменой URL в клиентском кабинете. Остановить старую автозагрузку согласованным способом без параллельной конкуренции двух источников. После первого реального импорта получить отчёт Avito: Id/AvitoId, число активных, исключения, снятия, отсутствие дублей. Ошибки сначала устранить в preview/ограниченном наборе. Финальная активация сейчас ожидает аккаунт и не выполнена.

## Ошибки и откат

Неудачный workflow сохраняет предыдущий remote snapshot; inspect failed Actions run, затем новый Run workflow с актуальным state. Non-fast-forward означает чужую запись в avito-feed: не force/rebase, повторить полностью после проверки владельца записи. Во время технического сбоя preview может оставаться старым; production по умолчанию закрывается после 4 часов. Проверять generated_at и stale, а не только HTTP200 preview.

Для аварийного закрытия production агент отключает только Avito workflow, затем публикует reviewed preview snapshot (без feed.xml, production_enabled=false), либо развёртывает relay с намеренно закрытым feed; исходный URL в Avito временно отключается по правилам кабинета. Возвращать один только старый feed при новом state запрещено. Для отката данных взять весь согласованный набор state/status/preview/report/CSV/feed из одного прежнего SHA и опубликовать новым fast-forward snapshot/pointer через snapshot.py. Старый generated_at должен остаться старым: stale gate нельзя обходить подменой времени. Надёжный возврат рабочего production требует нового успешного расчёта с выбранным reviewed state и проверки текущего каталога/отчёта. Снятия/изменения, уже принятые Avito, git-откатом автоматически не отменяются — агент сверяет и восстанавливает их в кабинете/новом фиде отдельно.


## Управление вариантами и ручной расчёт

При первичном выборе без сохранённого state используется минимальный offer UID в группе. Затем `items[productUID].variant_id` закрепляет выбор: перестановка YML или новый вариант с меньшим UID не заменяют опубликованный товар. Для осознанной смены агент задаёт `config.product_overrides[productUID].variant_id` точным offer UID из той же группы, проверяет preview/diff и получает нужное согласование изменения. Id/AvitoId родительского объявления сохраняются. Исчезновение/недоступность выбранного варианта не должны превращать объявление в другой вариант: проверить причину `selected_variant_missing`, `source_missing` или доступности и план снятия по подтверждённым retirement правилам. Отсутствие явно настроенного offer UID даёт blocker `configured_variant_missing`; исправить override или источник, не обходить защиту.

Пример расчёта из reviewed импортированного state в PowerShell:

```powershell
$stagingPath = Join-Path $env:TEMP ('photostyle-migration-' + [guid]::NewGuid().ToString('N'))
python avito-service/converter.py --config avito-service/config.json --source-url https://photostyle.ru/tstore/yml/a8b941bea8a7ee192c94ad5b5a0059eb.yml --state path/to/imported-state.json --out $stagingPath
```

Не создавать `$stagingPath` заранее и не указывать каталог last-good. После успеха агент проверяет все результаты нового snapshot и только затем передаёт этот каталог в `snapshot.py publish --directory path/to/avito-feed-checkout --stage $stagingPath`. Для восстановления прежнего расчёта нужен новый `--out`, а не перезапись старого каталога.


## Проверенная особенность Cloudflare runtime

В настройках Pages compatibility date проверена: `2026-11-27`. В live deployment исправлена причина немедленного `pointer_fetch_failed`: Cloudflare Workers не реализует `redirect: "error"` и выбрасывает исключение ещё до upstream запроса. Использовать `redirect: "manual"`; существующая проверка HTTP отклоняет 3xx и не следует по Location. [Документация Request Cloudflare](https://developers.cloudflare.com/workers/runtime-apis/request/). Не возвращать неподдерживаемый режим при обновлении relay. Обёртка `(...args) => globalThis.fetch(...args)` сохранена; она поддерживает receiver нативного вызова.

После исправления root проверил live `/health`: HTTP 200, source_count=3626, candidate_count=2656, stale=false. Полную сетевую сверку preview и проверку feed=503/state=404 агент развёртывания фиксирует отдельно. Успех Actions и HTTP не равен официальной валидации Avito: категории, реквизиты, миграция прежних объявлений и финальная активация по-прежнему ожидают разрешённого доступа к аккаунту.
