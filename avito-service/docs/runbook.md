# Эксплуатация PhotoStyle Avito

## Подключение владельцем

Один раз создать два repository Actions Secrets: `AVITO_CLIENT_ID` и `AVITO_CLIENT_SECRET` в [Vareria-s/photostyle](https://github.com/Vareria-s/photostyle/settings/secrets/actions). Значения принадлежат владельцу нужного аккаунта Avito. Не передавать их в чат, код, Issues или XML. Других переменных, CSV, JSON и ручных флагов активации нет.

Следующий cron автоматически продолжит работу; ждать необязательно — можно Actions → PhotoStyle Avito hourly snapshot → Run workflow. Срок токена берётся из ответа Avito; новый токен получается автоматически из той же пары. Если секреты отозваны или истекли права аккаунта, исправить сами ключи/доступы, не подставлять access token в конфиг.

## Порядок запуска и границы успеха

1. Python/Node тесты и локальная проверка atomic git publication.
2. Получение последнего корректного snapshot из `avito-feed`. Только подтверждённое отсутствие ветки при доступном репозитории означает первый запуск.
3. Однократное ограниченное скачивание Tilda YML в `RUNNER_TEMP/avito-source.yml`. Account prepare и preview читают одни байты.
4. `account.py prepare` получает API-данные и проверяет владельца, профиль, полную прежнюю выгрузку, IDs, категории/факты и миграцию. Перед расчётом сверяются сохранённые версии `state.provider_outbox` и текущий результат Avito. Квитанция относится к конкретному digest; ожидание провайдера не останавливает новый расчёт из текущего Tilda. Превышение безопасных границ очереди или ошибка проверки останавливают запуск. Exit 0 создаёт новый staging и закрытый plan; exit 2 останавливает запуск без публикации/переключения. Exit 3 разрешает обычный preview только при отсутствии обоих Secrets. Неполная пара — ошибка.
5. `snapshot.py publish` публикует полные файлы и immutable pointer одним fast-forward push. Ни профиль, ни приватный plan не включаются в staging.
6. `account.py commit` сверяет публичный digest, scope, свежесть и status, повторно читает профиль и меняет только управляемый feed при совпадении исходного профиля (CAS). Другие feeds, расписание и report_email сохраняются. Уже установленная цель не вызывает повторный POST. Кэш указателя до 60 секунд учитывается ограниченным ожиданием публичного файла; ошибка не запускает повторную публикацию старого snapshot.
7. `account.py verify` только наблюдает текущую загрузку Avito: она должна содержать этот feed и его точные байты, иметь `success`, полный набор ожидаемых Id/AvitoId и не иметь ошибок объявлений. Pending, чужой digest, неполный результат, `success_warning` и error не считаются завершённой интеграцией. Уже принятая идентичная выгрузка допустима: новый upload ID ради повторной проверки не требуется. Workflow завершается ошибкой с безопасным blocker-кодом. Следующий часовой запуск автоматически повторяет проверки, не требует согласия пользователя.

Avito загружает по сохранённому расписанию и лимитам аккаунта. `POST /autoload/v1/upload` запрещён как проверка: он игнорирует эти ограничения. Успешная HTTP выдача `feed.xml` и `production_enabled=true` подтверждают локальный snapshot, а не публикацию всех объявлений площадкой. Даже успешный verify не означает, что исключённые Tilda товары перенесены: смотрите `source_update_count`, `new_source_count`, `preserved_count`, `excluded_source_count` и причины в account report.

`source_sync_complete` и `source_sync_coverage=complete|partial` описывают полноту охвата Tilda; они отделены от `ready_for_profile_switch` приватного plan и приёмки файла провайдером. Безопасное переключение частичного каталога не означает, что перенесены все товары. Создание новых объявлений проката не поддерживается текущим сервисом: причина `rental_CREATE_not_supported_in_service` относится к реализации, не к запрету Avito.

Старые объявления сохраняются целиком, в том числе не связанные с текущим Tilda. Сопоставление допускается только по надёжной уникальной идентичности; новые неоднозначные товары не получают новых ID. Новое объявление допускается только после проверки отсутствия дубля, уникальности SKU и обязательных фактов по схеме. Недостаточная физическая доступность или неизвестные обязательные факты не заменяются придуманными значениями. Снятие чужих объявлений, платное продвижение и расширение расписания не выполняются.

Защита полноты сравнивает raw offers с прежним `source_count` и прошедшие проверку группы в том же allowlist с прошлым набором: по умолчанию порог 70%. `candidate_scope=validated_source_groups`, `eligible_uids` хранит проверенные группы до allowlist, `candidate_count` — их число после allowlist. `feed_ad_count` считает XML-объявления отдельно и не служит базой этого порога. UID, выбранный вариант и SKU/Id сохраняются при unavailable, пропавшем или временно невалидном товаре; подмена новым объявлением не допускается.

Для сопоставленных и новых карточек Title/Description проверяются по активной ветке схемы категории. Политика `truncate_word` сокращает текст по границе слова до действующего max; исходный и результат записываются в `text_transforms` и `text-changes.csv`. HTML описания преобразуется в текст. Если описание Tilda пусто, существующая карточка использует проверенное историческое Description с записью происхождения `historical_description`; при отсутствии обоих используется фактическое название с причиной `factual_title_description`. Цена не пропускается только из-за пустого или сокращаемого текста, но все остальные проверки карточки сохраняются. Одно слово длиннее допустимого предела или неподдерживаемое правило остаётся видимой причиной сохранения прежней карточки.

## Объективные препятствия

Пара ключей сама по себе не подтверждает права автозагрузки, тариф, пригодный прежний профиль или достаточность товарных данных. API-отказ, неизвестная структура схемы, отсутствие полной замороженной копии прежнего feed, неоднозначная миграция, неподдерживаемые обязательные поля, ноль безопасных обновлений или конкурирующее изменение профиля блокируют переключение. Отчёт объясняет конкретный blocker; владелец не должен вручную строить migration.json, править activation flags или category CSV. Технический агент исправляет поддержку схемы/данных по фактам либо честно фиксирует невозможность продолжения. [Контракт и происхождение API](account-contract.md).

Текущая реализация не обещает добавление всех новых товаров Tilda или поддержку каждой схемы Avito. Сверка настоящего аккаунта и live API выполняется только после ввода ключей. Тесты с mock API не заменяют эту приёмку.

Пользователь подтвердил: все товары в продаже новые. Это подтверждённый факт для состояния продаваемых товаров; дополнительный ввод Condition не требуется. Прокат исключён из этого правила. Допустимое значение поля и прочие обязательные свойства всё равно проверяются по схеме конкретной категории Avito.

## Приватность и резервный профиль

Исходный и целевой профили, scope и digest находятся в plan с правами только владельца внутри `RUNNER_TEMP/avito-account`. Plan нужен для сравнения и восстановления после неудачного подтверждения POST. После запуска он удаляется, artifacts не создаются. Это временный защищённый backup, не постоянный архив. Никогда не переносить plan в рабочее дерево, публичный snapshot, ZIP или step summary. Не печатать API responses и profile URLs; workflow summary содержит только фиксированные безопасные сообщения.

Для продолжения между запусками `state.provider_outbox` хранит до 256 версий с digest, именем feed, ожидаемыми Id/AvitoId, временем создания, статусом и SHA-256 отпечатками профиля. `provider_receipts` содержит проверенные квитанции с digest и идентификаторами. Полные профили, email, profile URLs и credentials в очередь не записываются. Контекст версий не теряется при почасовой публикации: `source_sku` и резервирование Id/variant_id сохраняют идентичность новых объявлений, ещё ожидающих AvitoId.

Каждый запуск продолжает свежий расчёт из текущего Tilda, включая цены и остатки, пока расписание Avito ожидает своей очереди. Поздний успешный результат может подтвердить любую сохранённую версию после сверки точных байтов и полного набора объявлений. Такая квитанция не присваивает `accepted` последнему файлу с другим digest. `provider_validation` относится к текущим байтам; `last_provider_receipt` может описывать более старую версию. Контекст старых версий отмечается подтверждённым или вытесненным только по проверенным идентификаторам. Подтверждённая история и квитанции очищаются по сроку 7 суток; неразрешённая pending-версия старше 7 суток либо более 256 сохраняемых версий блокируют продолжение (`provider_outbox_unresolved_over_7_days`, `provider_outbox_limit_exceeded`), а не удаляются молча. Счётчики: `provider_versions_pending`, `provider_versions_retained`.

Если профиль после неудачного переключения всё ещё точно совпадает с исходным отпечатком, сервис проверяет контрольные данные опубликованной версии и восстанавливает приватный plan через новый расчёт из текущего Tilda. Устаревший snapshot не копируется с новой датой. Для свежего (не старше 4 часов) файла с неизменившимися байтами сохраняется исходное `data_generated_at`; обновление устаревшего файла требует действительного пересчёта. Если профиль уже целевой, обычный расчёт продолжается со сверкой очереди; постороннее изменение профиля блокирует переключение.

Если ответ POST потерян, account commit проверяет фактический профиль и пытается восстановить прежний только при точном совпадении собственного изменения. Код `rollback_unconfirmed` означает, что восстановление не доказано: технический агент сверяет кабинет и последнюю операцию, не повторяет POST вслепую. Уже обработанные Avito изменения Git-откатом не отменяются.

## Наблюдение и повторный запуск

Проверять Actions → последний run и безопасный blocker-код. JSON `/health`, `/status.json`, `/report.json` показывают **последний опубликованный** snapshot; `provider_status_as_of=prepare` означает наблюдение на этапе подготовки, а окончательный результат после публикации находится в Actions → account verify (`account_verify_ok` при успехе), как указано в `provider_status_channel`. Private plan обновляется после проверки, публичный snapshot этим шагом не переписывается; ошибка новой попытки не переписывает его фиктивным результатом. `/preview.xml` может оставаться старым; проверять `generated_at` и stale, не один HTTP 200. Production закрывается после 4 часов по умолчанию (`STALE_HOURS` в Cloudflare).

Prepare failure оставляет прежние snapshot/profile. Publish failure не позволяет перейти к account commit. После успешной публикации commit/verify failure оставляет опубликованный snapshot; это не атомарная транзакция между GitHub и Avito. Проверить фазу и blocker, затем повторить полный run с актуальным remote state. Non-fast-forward — ошибка конкуренции: не force/rebase, установить владельца записи и повторить весь запуск. Не отключать PDF workflow.

Для аварийного закрытия технический агент останавливает только Avito workflow и закрывает выдачу feed согласованным способом либо публикует согласованный preview snapshot. Для отката данных взять **весь** snapshot из одного прежнего SHA и опубликовать новым fast-forward pointer через `snapshot.py`; не смешивать state/status/feed разных версий и не подменять generated_at. Вернуть текущую корректную production можно только новым расчётом и проверкой провайдера. Для остановки загрузки Avito требуется отдельная проверка его профиля и расписания.

## Размещение и проверки разработчика

Изменять только `avito-service/` и `.github/workflows/photostyle-avito.yml` в main. PDF, корневой README репозитория и его workflows не затрагивать. Actions использует встроенный `GITHUB_TOKEN` с `contents:write`, отдельный PAT не нужен. Concurrent runs сериализованы, отмены активной публикации нет. Cron работает с default branch; задержки GitHub возможны.

Relay размещён отдельно: [photostyle-avito.pages.dev](https://photostyle-avito.pages.dev). Pages ZIP загружать в тот же отдельный проект Direct Upload, не в photostyle-documents. ZIP содержит три файла в корне и Advanced-mode worker. Cloudflare runtime требует `redirect: "manual"` с отказом на 3xx; режим `redirect: "error"` здесь не реализован. Не менять сохранённую обёртку native fetch без проверки.

После развёртывания проверять GET/HEAD `/health`, `/preview.xml`, `/report.json`; `/feed.xml` закрыт до готовой account подготовки, `/state.json`=404, POST=405. Текст корневой страницы статичен и не заменяет JSON/Actions. Сетевая проверка HTTP не равна Avito acceptance.

```powershell
python -m unittest discover -s avito-service/tests -v
node --test avito-service/tests/worker.test.mjs
python avito-service/tools/check_publication.py
python avito-service/tools/package.py --out work/packages
```

Упаковщик читает только явный список публичных исходников; произвольные reports/runtime files не включаются. После изменения состава проекта обновить allowlist и проверить содержимое обоих ZIP. Account plan никогда не сохранять даже под именем разрешённого исходника.
